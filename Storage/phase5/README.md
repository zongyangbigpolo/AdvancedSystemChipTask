## 2. ST-P5-01：数据格式与确认契约

在 `$LAB/src/wal_store/` 编写 `put/get/scan/recover` 接口、测试客户端和校验器。初始单写者，文件锁拒绝第二个 writer；reader 在恢复建立索引后读取，不宣称支持并发事务隔离。

记录包含 magic、格式版本、record length、sequence、操作类型、key/value 长度和 CRC，明确字节序及最大长度。CRC 覆盖元数据与 payload；分配内存前验证长度、偏移溢出和剩余文件边界，不根据不可信 length 任意分配。重复 key 取最高有效 sequence 的值，删除采用 tombstone。

基础提交次序：

```text
校验请求 → 完整追加 record（处理短写/EINTR）
→ fdatasync 成功 → 更新可见内存索引 → 向客户端返回 durable ack
```

初次创建 WAL 后同步其父目录，明确文件存在性的持久化；之后使用同一文件。`none` 模式只确认进入 OS，不标作 durable。错误后的实例进入明确失败/只读状态，不能在序号/索引不确定时继续返回成功。

恢复先只读扫描：按格式与 CRC 重建状态。尾部未完整 record 可视为未确认尾巴，在记录诊断并保留副本后按契约截去；**中间 record 损坏、序号倒退或已确认范围缺失应失败**，不跳过坏块拼出“成功数据”。尾部 CRC 错误也需与 ack 对照，不能无条件当未提交数据丢弃。

需测试 key 覆盖、tombstone、空 value、最大 value、非法长度、部分 header/payload、错误 CRC 和损坏中间记录。校验器用独立参考字典重放，而不是复用同一恢复函数作为唯一 oracle。

## 3. ST-P5-02：group commit 与快照发布

按“每条同步”和“最多 8/32 条或最多等待 2 ms 后同步”对照。超时即使不足批量也提交；只有同一批全部日志完整写入且 fdatasync 成功后，才能 ack 该批。请求延迟从到达队列开始计入，包括等批时间。

快照至少携带格式、checksum、最后包含的 sequence。采用以下保守流程：

1. 暂停新提交，排空当前批并同步 WAL；此时得到一致的索引与 sequence S。
2. 在同一实验目录写独立临时快照文件，完整写入并 fsync。
3. 原子 rename 为快照文件名，再 fsync 父目录；失败时保留旧快照和全部 WAL。
4. 恢复时读有效快照，再从仍保留的 WAL 重放 `seq > S` 的记录。

基础版本**不删除或截断旧 WAL**，以免把日志回收问题混入快照正确性；快照仍减少索引重建工作，但读文件/定位开销须如实测量。若扩展分段与回收，需额外设计持久 manifest、段发布/目录同步及崩溃排序，证明不再需要旧段后才删除，不简单用 rename 后清空 WAL。

对临时文件写到一半、rename 前后、父目录 fsync 前后设置程序级停止点。两组都使用同一初始数据与 ack 契约；不要一组关闭同步后一组开启，却只按吞吐排序。

## 4. ST-P5-03：可重复的故障矩阵

测试驱动作为独立父进程，通过 pipe/socket 向存储子进程发送确定性请求。收到 ack 后记录 `{request ID, sequence, value CRC}` 到独立 oracle；测试前规定只有 durable ack 才进入“必须恢复”集合。oracle 写入/同步不要放在被测试 WAL 或同一受损文件内，记录其对负载的扰动。

| 注入点 | 方法 | 预期行为 |
| --- | --- | --- |
| 短写/EINTR | 在本程序 I/O 包装层按固定 seed 注入 | 正确补写/重试，不丢偏移、不重复 ack |
| ENOSPC | 独立小容量实验文件系统，或包装层模拟 | 写入/同步失败显式返回，未完成请求不 durable ack |
| EIO | 写或 fdatasync 包装层返回确定错误 | 对应批次失败，不能更新已提交索引并继续成功 |
| append 中途/同步前后 | 应用断点通知父进程，再终止**该子进程** | 重启恢复所有已收到 durable ack 的记录；未 ack 可存在或不存在 |
| snapshot 发布各步骤 | 每个停止点各生成独立数据副本 | 恢复旧或新合法快照并补 WAL，不丢已确认数据 |
| 尾部/中间损坏 | 仅修改已关闭 WAL 的具名副本 | 尾部按契约诊断；已确认或中间损坏明确失败 |

父进程保存自己创建的精确 PID，在指定点终止该 PID，不按进程名 kill，也不对整台主机故障注入。收到“即将同步”事件并不等于已完成同步，需要在明确前后不同点分别测试。

在 append→sync→ack 之间，可能出现“数据已保存但客户端未收到 ack”，恢复包含这些记录是允许的；重试 API 需定义 request ID 去重或明确是至少一次语义，不能重复执行非幂等动作后仍声称恰好一次。

至少覆盖 20 个固定 seed、每个关键停止点，记录注入序号、返回码、最后 ack、恢复结果及错误信息。对缺失 ack、错误 value、错序和无声跳坏块设置校验器非零返回。

**边界：**杀进程不会清除内核 page cache 或设备易失写缓存；该矩阵证明的是进程级恢复和错误处理。真实 OS 崩溃/掉电仅在独占主机与批准硬件设施中另做，记录 PLP、虚拟化层、缓存与 Flush 支持；没有测试就不填写“掉电零丢失”。

## 5. ST-P5-04：综合运行与完成标准

固定 key 数、value 大小 128 B/4 KiB/64 KiB、读写比例和请求总量，比较每条同步与分组提交。每格三轮，报告从客户端到 ack 的平均/P95/P99、吞吐、批等待、sync 耗时、WAL 字节数与恢复时间。恢复阶段统计 scan 字节数、有效 record 数及最终字典散列，不能只看程序退出码。
