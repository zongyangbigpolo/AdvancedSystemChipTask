## 2. NPU-P4-01：建立 Add 实现

从所选 CANN 版本附带的 Ascend C 样例或官方文档入口获取 Add 样例，登记包版本、commit、许可证和目标 SoC。不同发布版的生成模板与构建脚本可能变化，以配套 README 的工程生成、编译和安装命令为准，不把任一历史仓库路径当作所有版本入口。

先原样编译运行，再在实验目录建立自己的算子工程：

```text
输入检查 → 主机计算 tiling 参数 → 选择 block 数
每个 block 计算独立全局区间
按 tile 搬入 x/y → 向量加法 → 搬出 z
执行完成同步 → 与 CPU z=x+y 比较
```

交付主机 tiling、kernel、算子定义/注册、构建配置、输入生成和校验程序。设备端地址范围、局部存储分配、队列入出和同步必须匹配；不能只交安装生成物。

## 3. NPU-P4-02：边界与错误处理

覆盖元素数 1、31、32、33、255、256、257、4096、1000003；这些是元素数，不是字节数。使用 FP16，并在实际支持时增加 FP32，分别测试零、正负交替和固定种子随机输入。

尾块采用产品支持的带 padding 数据搬运、mask 或独立尾段方案；不得越界读取后通过丢弃输出来掩盖问题。对长度不一致、dtype 不匹配、设备内存不足和非法 tiling，主机接口明确报错。空输入仅在框架/算子契约允许时接受并单列。

使用该 CANN 版本支持的仿真/算子检查工具定位问题；工具不可用时明确记录，至少运行全部边界与 guard 区检查，不宣称完成了不存在的 sanitizer 覆盖。

## 4. NPU-P4-03：tiling 与流水

根据该 SoC 的 UB 容量和对齐规则计算每个输入、输出、队列的占用；例如更大的 tile 和双缓冲会增加局部存储需求，不能任意把样例参数加倍。

先固定 block 数，比较三种合法 tile；再固定 tile 比较单缓冲与双缓冲。每组先过边界测试，预热后测设备事件与端到端时间。用配套 profiler 查看搬运、向量计算及等待；并非所有 SoC 都提供相同计数指标。

报告有效带宽时，Add 的逻辑读写量为 `3 × N × sizeof(dtype)`；这是算法有效字节量，不等同于硬件实测内存总线流量。

## 5. NPU-P4-04：融合与集成

实现 `z=ReLU(x+y)`，融合 kernel 不写回中间张量。按实际版本的自定义算子注册接口接入 torch_npu 或 AscendCL，保存接口签名、dtype、shape 推导和加载路径。避免覆盖全局正在使用的算子包，使用实验隔离路径。

对照框架 `relu(x+y)` 的实际图优化结果：若框架已自动融合，应记录为“已融合基线”，不能再把差值归因为省去一次 kernel。分别测 1 Ki、64 Ki、1 Mi 元素及非整齐尾块，检查数值一致性。
